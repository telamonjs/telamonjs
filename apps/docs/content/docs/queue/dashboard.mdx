The **Jobs Dashboard** is a complete React monitoring UI for BullMQ queues, shipped
in the `@telamonjs/ui/queue` subpath. It talks to your backend through a
pluggable **adapter** (NestJS, Next.js or custom) and uses React Query for data
fetching plus **Server-Sent Events (SSE)** for real-time updates.

Features:

- **Real time** — live queue stats, job event timeline (started / completed /
  failed / progress / retrying) over SSE with automatic reconnection and graceful
  degradation to polling when SSE is unavailable
- **History** — completed/failed job history across all queues with search, date
  range filters and aggregate stats
- **Queue actions** — pause, resume, clean, retry-all, drain; per-job retry,
  remove, promote; bulk retry/remove; manual job dispatch
- **Job configuration** — enable/disable jobs (per job or per module), edit cron
  pattern, priority, concurrency and timeout at runtime, with a change history
  audit trail
- **Redis metrics** — connection utilization and health

## Mounting in your app

The plug-and-play entry point is `QueueTabbedDashboard` — a shell page with four
lazy-loaded tabs (`tempo-real`, `configuracao`, `redis`, `historico`) built on the
canonical TelamonJS shell (`ShellPage` + `AdminHeader` + `AdminTabs`).

```tsx title="app/admin/jobs/page.tsx"
'use client'

import {
  QueueTabbedDashboard,
  QueueApiProvider,
  createNestJSAdapter,
} from '@telamonjs/ui/queue'

const adapter = createNestJSAdapter({
  baseUrl: process.env.NEXT_PUBLIC_API_URL!,
  getAuthToken: async () => {
    const session = await getSession()
    return session?.user?.accessToken ?? null
  },
})

export default function JobsPage() {
  return (
    <QueueApiProvider adapter={adapter}>
      <QueueTabbedDashboard syncTabWithUrl />
    </QueueApiProvider>
  )
}
```

<Callout type='info' title='Auto-provider'>
  If no `QueueApiProvider` is present, `QueueTabbedDashboard` creates a NestJS
  adapter automatically from `apiUrl` (default:
  `process.env.NEXT_PUBLIC_API_URL`, falling back to relative URLs). Wrapping it
  explicitly is only needed for custom adapters or auth logic.
</Callout>

### QueueTabbedDashboard props

| Prop             | Type                       | Default                             |
| ---------------- | -------------------------- | ----------------------------------- |
| `initialTab`     | `'tempo-real' \| 'configuracao' \| 'redis' \| 'historico'` | `'tempo-real'` |
| `tabs`           | subset of the four tab ids | all four                            |
| `title`          | `string`                   | `'Central de Jobs'`                 |
| `description`    | `string`                   | queue monitoring subtitle           |
| `icon`           | `ComponentType`            | —                                   |
| `moduleIcons`    | `Record<string, ReactNode \| IconComponent>` | — (module group icons: emoji, node or icon component) |
| `moduleLabels`   | `Record<string, I18nText>` | — (module group titles; key order = group order) |
| `jobLabel`       | `(jobName: string) => I18nText \| undefined` | — (job label override) |
| `enableSSE`      | `boolean`                  | `true`                              |
| `pollInterval`   | `number` (ms)              | `2000` (timeline polling while SSE is down) |
| `syncTabWithUrl` | `boolean`                  | `false` (reads/writes `?tab=` param)|
| `onTabChange`    | `(tab: string) => void`    | —                                   |
| `apiUrl`         | `string`                   | `process.env.NEXT_PUBLIC_API_URL`   |

### Module and job labels

Jobs are grouped by **module**, the prefix of the job name (`comunicacoes_enviar-email`
belongs to `comunicacoes`). Module keys and job names are Redis keys, so they cannot
carry accents or spaces. Three props turn them into real names:

- `moduleLabels` sets the group titles in the Real-time and Configuration tabs. Its key
  order is also the group order in both tabs. Modules it does not list follow,
  alphabetically by label. Without it, groups show the raw key, capitalized, in
  alphabetical order.
- Job labels follow one precedence, first match wins:
  1. `jobLabel(jobName)`, when it returns something other than `undefined`;
  2. the job contract's `displayName`, which `@telamonjs/queue` serves as the contract's
     short `label`, else its `description`;
  3. the formatted job name: the module prefix is removed and the words are capitalized,
     so `comunicacoes_enviar-email` becomes "Enviar Email".

  Set `label` on the contract to keep long `description` sentences out of the rows. The
  label is used in queue rows, timeline and history rows, job details, modal titles and
  the `JobDetailPage` title, which also shows the contract's `description` below it.
- `moduleIcons` takes an emoji, any React node, or an icon component such as a Lucide icon.

Text values are `I18nText`: a literal, or `msg('key')` resolved in the active locale.

```tsx title="app/admin/jobs/jobs-dashboard.tsx"
'use client'

import { Mail, Wrench } from 'lucide-react'
import { msg } from '@telamonjs/ui'
import { QueueTabbedDashboard } from '@telamonjs/ui/queue'

const moduleLabels = {
  comunicacoes: 'Comunicações',
  manutencao: msg('jobs.modules.maintenance'),
}
const moduleIcons = { comunicacoes: Mail, manutencao: Wrench }
const jobLabels: Record<string, string> = {
  'manutencao_limpar-audit-logs': 'Limpar logs de auditoria',
}

export function JobsDashboard() {
  return (
    <QueueTabbedDashboard
      moduleLabels={moduleLabels}
      moduleIcons={moduleIcons}
      jobLabel={name => jobLabels[name]}
    />
  )
}
```

<Callout type='warn' title='Functions do not cross the server boundary'>
  `jobLabel` and icon components are functions, so a Server Component cannot pass them to
  `QueueTabbedDashboard`. Set them in a Client Component, as above.
</Callout>

## Adapters

An adapter implements the `QueueApiAdapter` interface (or the superset
`QueueConfigApiAdapter`, which adds job configuration and SSE methods). Two
factories ship with the package:

const adapter = createNestJSAdapter({

## Expected server contract

The dashboard is backend-agnostic — whatever the adapter resolves is what renders.
The reference NestJS backend exposes this REST surface (all under `/v1`):

| Method   | Endpoint                                  | Purpose                                        |
| -------- | ----------------------------------------- | ---------------------------------------------- |
| `GET`    | `/v1/queue/stats`                         | `DashboardStats` — totals + per-queue stats    |
| `GET`    | `/v1/admin/metrics/redis`                 | Redis connection metrics                       |
| `GET`    | `/v1/queue/jobs?queue&state&limit`        | Jobs of one queue/state                        |
| `GET`    | `/v1/queue/jobs/all?status&queue&search&limit&offset` | Jobs across all queues, filtered   |
| `GET`    | `/v1/queue/history?queue&limit`           | History of one queue                           |
| `GET`    | `/v1/queue/history/all?statuses&queue&search&startDate&endDate&limit&offset` | Global history + aggregate stats |
| `POST`   | `/v1/queue/actions`                       | `{ type, queueName, status? }` — pause/resume/clean/retry-all/drain |
| `POST`   | `/v1/queue/jobs/retry` / `remove` / `promote` | `{ queueName, jobId }` single-job actions  |
| `POST`   | `/v1/queue/jobs/bulk`                     | `{ queueName, jobIds, operation }` bulk retry/remove |
| `GET`    | `/v1/queue/dispatch`                      | List manually dispatchable jobs                |
| `POST`   | `/v1/queue/dispatch`                      | `{ queueName, data }` — dispatch a job         |
| `GET`    | `/v1/queue/config`                        | All job configurations                         |
| `GET/PATCH` | `/v1/queue/config/:jobName`            | Read / update one job config                   |
| `POST`   | `/v1/queue/config/:jobName/toggle`        | Enable/disable a job                           |
| `POST`   | `/v1/queue/config/modules/:module/toggle` | Enable/disable all jobs of a module            |
| `GET`    | `/v1/queue/config/:jobName/history`       | Config change audit trail                      |
| `GET`    | `/v1/queue/events`                        | **SSE stream** (stats + job events)            |

Contract notes (enforced by the reference backend and reflected in the adapter
types):

- `queueName: '*'` (all queues) is only accepted with `type: 'clean'` — any other
  action targeting `'*'` returns 400.
- `startDate`/`endDate` are ISO 8601 strings; unparseable dates return 400.
- `limit` must be an integer from 1 to 500 and `offset` an integer `>= 0`;
  `state`/`status` must be a known job state (`statuses` on `history/all`:
  `completed`/`failed`). Anything else returns 400.
- `PATCH /config/:jobName` and `POST /config/:jobName/toggle` return 404 for a job
  with no stored config. The PATCH body is validated (`cronPattern` a valid cron
  pattern, `priority` an integer from 1 to 10, `concurrency`/`timeout` positive
  integers, `null` clears a field) and the toggles require a boolean `enabled`;
  invalid input returns 400.
- History/jobs responses may set `approximate: true` when `total` is a
  post-filter count (active search/date filters).
- The SSE endpoint requires the `jobs.execute` permission in the reference
  backend — the connection is rejected otherwise.

### Protecting the routes

`QueueHttpModule.forRoot()` (from `@telamonjs/queue/nestjs`) declares no
permission on its routes unless you ask it to. With the usual global auth and
permissions guards, that means every logged-in user can dispatch jobs, remove
them and edit job configs. Set both options:

```ts
QueueHttpModule.forRoot({
  depsFactory: () => ({ queues, jobConfigStore, contracts, eventBroadcaster }),
  getActor: req => req.user.email,
  readPermission: 'queue.read',   // every GET route, the SSE stream included
  writePermission: 'queue.write', // every POST/PATCH route
})
```

Each option takes what `@Permissions(...)` from
[`@telamonjs/permissions`](/docs/packages/permissions) takes: a string, or a
list of clauses (OR between entries, an inner array is AND). They are written as
the metadata that package's guard reads, so that guard (global, or in `guards`)
is what enforces them.

Guards run once per request, and the SSE stream is one long request. The route
ends each stream after `sseMaxAgeMs` (a `forRoot()` option, 5 minutes by
default) and the dashboard reconnects through your guards, so an expired token,
a revoked session or a removed `readPermission` stops the feed within that time.
The stream's last frame is `event: reconnect`, so the dashboard reconnects at
once and keeps showing `connected`. A client that stops reading is dropped
sooner: once 1 MiB of frames is waiting for it, the route closes the stream.

## Real-time updates (SSE)

With `enableSSE` (the default), the dashboard connects to the adapter's
`getSSEConfig()` URL and feeds the React Query cache:

- **Stats updates** pushed by the server (~5s cadence) refresh the queue cards
- **Job events** (`job:started`, `job:completed`, `job:failed`, `job:progress`,
  `job:retrying`) update the live timeline in real time
- Rapid event bursts are debounced into a single stats refetch
- Automatic reconnection with status reporting
  (`connecting | connected | disconnected | error`)
- If the adapter does not implement `getSSEConfig()`, the dashboard falls back to
  React Query polling
- The live timeline polls every `pollInterval` only while SSE is down; with the stream
  connected it polls every 30s as a safety net, and not at all while another tab is open

## Other components

The tabs, modals, tables and data hooks inside the dashboard are internal. Besides
`QueueTabbedDashboard`, the subpath exports two more ready-made screens (both under the same
`QueueApiProvider`):

```tsx
import { QueueDashboard, JobDetailPage } from '@telamonjs/ui/queue'

// Single-page (non-tabbed) dashboard: stats cards + per-queue table with actions
<QueueDashboard pollInterval={10000} showHeader settingsHref='/admin/jobs/config' />

// Configuration + change history of one job (fetched through the adapter)
<JobDetailPage jobName='send-email' backHref='/admin/jobs' onRefresh={() => router.refresh()} />
```

| `JobDetailPage` prop | Type | Description |
| --- | --- | --- |
| `jobName` | `string` | Job whose config and history are fetched |
| `apiUrl` | `string` | API URL override (default: env var) |
| `config` / `history` | `JobConfig` / `JobHistoryEntry[]` | Pre-fetched data; skips the fetch |
| `backHref` / `onBack` | `string` / `() => void` | Back navigation |
| `onRefresh` | `() => void` | Called after a successful update |
| `moduleLabels` / `jobLabel` | as on `QueueTabbedDashboard` | Module badge and title; pass the dashboard's values |

The header `QueueDashboard` renders with `showHeader` is exported as `QueueDashboardHeader`, and
the display config of a job state (icon, label, colors) as the type `JobStatusConfig`:

```tsx
import { QueueDashboardHeader, type JobStatusConfig } from '@telamonjs/ui/queue'
```

<Callout type='warn'>
The older names `DashboardHeader` and `StatusConfig` are still exported from
`@telamonjs/ui/queue` but deprecated: the root barrel has a `DashboardHeader` (the
`DashboardShell` header) and a `StatusConfig` (the `DetailStatus` config) that are different
symbols.
</Callout>

Types (`QueueStats`, `DashboardStats`, `JobInfo`, `JobConfig`, `JobHistoryEntry`,
`QueueApiAdapter`, `QueueConfigApiAdapter`, …) are exported from the same subpath.

## Bull Board (server-side dashboard)

Independently of the React dashboard, `@telamonjs/queue/dashboard`
ships an embeddable **Bull Board** UI for low-level queue inspection:

```typescript
import { startDashboard } from '@telamonjs/queue/dashboard'

// Standalone Express server (default port 3005)
const dashboard = startDashboard({
  port: 3005,
  queueManager,
  auth: {
    enabled: true,
    username: 'admin',
    password: process.env.DASHBOARD_PASSWORD!,
  },
})

// The app owns shutdown: startDashboard installs no signal handlers
process.on('SIGTERM', () => dashboard.server.close())
```

`startDashboard` returns the Express app with the listening HTTP `server`
attached, and also exposes a `/health` endpoint listing registered queues.

Or mount it into an existing Express app:

```typescript
import { createDashboardRouter } from '@telamonjs/queue/dashboard'

const app = express()
app.use(
  '/admin/queue',
  createDashboardRouter({
    queueManager,
    auth: { enabled: true, username: 'admin', password: process.env.DASHBOARD_PASSWORD! },
  })
)
```

Express 4 and 5 are both supported, so the router mounts into a Nest 11 app's
Express 5 as well.

Basic-auth protection is opt-in via the `auth` config, and both functions honor
it — always enable it outside local development. `auth.enabled: true` with a
missing or empty `username` or `password` throws a `ConfigurationError` at
startup instead of serving the board unprotected.
